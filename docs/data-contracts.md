# QuantStone 数据对接

数据通过 `quantstone-data/sdk/python` 的 `QuantStoneClient` 读取，不直接访问服务端存储文件。SDK 要求 Python >=3.11。仅读取数据，不触发采集、修复或服务重启。

| 数据集 | 用途 | 适配规则 |
| --- | --- | --- |
| `tushare.cn.stock.daily` | 日线、分钟策略日线窗口 | 未复权价格；`vol` 手转股；09:30 开始、15:00 结束 |
| `tb_sbkj2077.cn.stock.minute_1m` | 分钟回放 | `volume` 手转股，`bar_time` HHMMSS 按显式标签配置解释 |
| `tushare.cn.stock.trade_cal` | 交易日调度 | 快照整表读取，过滤 SSE，再本地按区间与 is_open 过滤 |
| `tushare.cn.stock.stk_limit` | 撮合涨跌停约束 | 按股票和日期匹配，缺失时失败 |
| `tushare.cn.stock.adj_factor` | 检测未支持的公司行动 | 区间内因子变化时失败，不直接复权成交价 |

日线预取开始日前 45 个自然日作为历史窗口，实际数量取决于数据存在情况。分钟线按单只股票、每七个自然日分批获取，不在每个事件中发 HTTP 请求。当前全量所需 Bar 在内存中，未实现持久化行情缓存；最多 500000 根分钟线。

## 2026-11-27 实测发现

1. 交易日历已有快照（13493 行）。携带 `start/end` 读取时，服务返回“数据集尚无已发布数据”；去掉日期过滤能正确读取。因此适配层对快照不发送日期范围。这是读取方式兼容处理，未修改上游项目。
2. 股票分钟契约将 `bar_time` 描述为“开始时间”，但 `000001.SZ` 的 2026-11-02 样本共有 241 行：09:30、09:31…11:30、13:01…15:00。这与连续竞价结束标签的分布一致，与声明的开始标签冲突。
3. 因此本版提供 `minute_label=end/start`。默认 `end` 为根据实测分布作出的适配假设：09:31 映射为 09:30–09:31，15:00 映射为 14:59–15:00；跳过额外的 09:30 记录，不将其并入第一根成交量。尚未独立核实该记录的供应商定义。
4. 使用者可以显式选择 `start` 按契约解读；此时不合法的时段（例如 15:00 起始一分钟）会报错，不会被静默移到下一分钟。
5. 每个结果记录标签模式、跳过的 09:30 行数、数据集列表及时间区域。后续应推动上游确认时间语义并修正文档，再收敛默认配置。

已使用真实服务对 `000001.SZ`、2026-11-02 至 2026-11-04 完成日线与分钟线端到端回测。日线加载 28 根（含预热历史）；分钟任务加载共 748 根（含 28 根日线），跳过 3 条 09:30 记录。验证属于窄区间集成检查，不代表全市场数据质量已经确认。
